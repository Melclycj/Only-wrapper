<objective>
Fix GAP-12-B: the TERM-05 startup-command readiness probe times out under heavy login-shell rc-init latency
because `READINESS_TIMEOUT_MS` is a FIXED 4000ms. The diagnosis (`.planning/debug/gap-12-b-restart-probe-timeout.md`,
status: diagnosed) CONFIRMED + REPRODUCED the root cause: the probe match time ≈ rc-init time (the `\n…<nonce>`
match can only fire after the login shell finishes rc and re-prompts), and the 4000ms wall is shared by BOTH the
dormant-Start and the restart-respawn paths (`create()` is the single funnel) — this is a latency-budget defect,
NOT a restart-vs-dormant code divergence. Do NOT re-diagnose.

The fix is a DUAL-DEADLINE budget (typescript-reviewer flagged the absolute ceiling as LOAD-BEARING):
1. RAISE the base idle window above the current 4000ms and make it EXTEND-ON-PROGRESS — reset the deadline each
   time the probe interceptor sees new bytes (a slow-but-progressing rc is not guillotined at a fixed wall).
2. ADD A MANDATORY HARD ABSOLUTE CEILING (`READINESS_HARD_TIMEOUT_MS`) measured from probe-arm time — a
   chatty-but-never-ready shell that streams ≥1 byte per idle window would extend forever and NEVER inject without
   this cap. Both timers call the SAME flush-and-notice cleanup (D-04: never inject on timeout).

DEBT-02: the regression test MUST exercise the REAL failure timing. Build it from the spike-005 heavy-init
ZDOTDIR-sleep driver (which deterministically makes the OLD probe time out), NOT the fast-env wdio smoke that
passes falsely. Relocate the two parked `.diag.test.ts.txt` stubs in `.planning/spikes/005-restart-probe-timeout/`
into committed regression tests (the main/bad-cwd one lands in THIS plan; the renderer/surface one lands in 12-09).

Purpose: a stored startup command actually auto-runs on a real (slow-rc) machine after a restart-to-apply, while a
genuinely-hung shell still falls back safely — closing the operator's #5 re-gate failure.
Output: the dual-deadline budget in create(), the new exported timeout constants, a real-timing integration
regression, and the relocated main-side bad-cwd regression test.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| freshly-spawned login shell → create() probe interceptor | The shell's rc output (arbitrary bytes, attacker-influenceable via a poisoned rc) crosses into the probe buffer before any match |
| the readiness budget timers → renderer | A timeout decides whether the buffered output is flushed + a notice sent; an unbounded wait would block the auto-run outcome indefinitely |
| create() cwd → pty.spawn | A bad/missing working directory must not reach pty.spawn (unchanged CR-01) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-08-01 | Denial of service | a chatty-but-never-ready shell extending the idle deadline forever | mitigate | The MANDATORY hard absolute ceiling READINESS_HARD_TIMEOUT_MS=15000ms is measured from probe-arm and is NEVER reset by the idle-extend logic; it fires the SAME flush-and-notice give-up path, so a stream-forever shell cannot postpone the timeout (typescript-reviewer LOAD-BEARING item) |
| T-12-08-02 | Denial of service | the readiness wait stalling the UI / blocking the main process | mitigate | The probe is fully ASYNC/non-blocking — onData + setTimeout; the main process never busy-waits. Pre-match bytes are buffered (bounded scan to last 8KB in buildPosixProbe, WR-03); raising the budget changes only WHEN the (async) fallback fires, never blocks the event loop. The renderer is unaffected until the (async) flush or notice |
| T-12-08-03 | Information disclosure | probe nonce / buffered rc bytes leaking to renderer/logs pre-match | mitigate | D-02 invisibility UNCHANGED: the interceptor buffers and NEVER calls this.send() pre-match; on match the buffer is discarded; lifecycle logging only (no command/nonce/buffer logged, V7). The idle-extend adds no new send and no new log of buffer contents |
| T-12-08-04 | Tampering | a bad cwd reaching pty.spawn on the respawn | accept | UNCHANGED — CR-01 isValidCwd in updateProfile + create()'s pre-spawn cwd validation stay the validator of record; this plan does not touch the cwd path. (The bad-cwd regression test in Task 2 pins this behavior.) |
| T-12-08-05 | Tampering | npm install of a new package | accept | NO new dependency — node-pty + vitest already present; the integration test is plain node + the existing node-pty. No package-manager install task |

## Reliability & Cost (§6.5)
GAP-12-B is a cost/latency-budget change, so the R&C lens is central. (1) RESOURCE/COST RUNAWAY: the hard absolute
ceiling (T-12-08-01) is the explicit guard — without it a never-ready shell would wait forever; with it the worst
case is bounded at 15s then a clean fallback. (2) NO INJECTION ON A NEVER-READY SHELL: the command is injected
ONLY on a real probe match; both timeout paths (idle + hard) flush a bare prompt and emit the notice and NEVER
best-effort inject (D-04) — a never-ready shell yields a usable bare shell, not garbled keystrokes. (3) NO UI
STALL: the probe is async/non-blocking (T-12-08-02) — raising the timeout cannot stall the renderer or the main
event loop; it only delays an async fallback. (4) NO RETRY STORM / NO AMPLIFICATION: there is ONE marker write and
ONE outcome per spawn; no retry loop is added (the optional retry from the diagnosis is intentionally out of
scope). (5) NO TOKEN/LLM COST. Terminal fidelity is untouched — create() stays the single funnel and the bare-shell
/ match-inject paths are unchanged.
</threat_model>
