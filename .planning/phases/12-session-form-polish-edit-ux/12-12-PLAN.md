<objective>
Fix the CONFIRMED GAP-12-E precedence bug (`12-VERIFICATION.md` §"Re-Gate 2 Result" + the round-3 reopened-gaps
table; root cause code-confirmed). Implement the operator's directive verbatim; do NOT re-investigate.

THE BUG (confirmed): in `handleSaveProfile` (SessionManager.tsx ~:413), `setRestartPromptId(promptId)` runs
SYNCHRONOUSLY before the async drop-check (the `void (async () => { … cwdDropNoticeFor … })()` block at ~:398–409
which awaits `rehydrateProfiles()` then sets the cwd-drop notice) resolves. So on a running session with a dropped
cwd AND changed launch fields, the "Restart to apply?" prompt pops FIRST and the drop notice queues behind it
(the code comment at ~:412 even admits "the prompt still queues behind it").

THE OPERATOR DIRECTIVE (verbatim, round-3 gate): "if the path is wrong, user can not press save, on click save,
the check must detect that path is invalid, display the inline reminder, rather than letting user continue to
click save." → An invalid/dropped path must BLOCK the save: show the inline reminder, KEEP the modal open, and
SUPPRESS the restart prompt entirely. Only a clean save (no drop) closes the modal and (if launch fields changed
on a live session) shows the restart prompt.

THE FIX: move `setRestartPromptId(promptId)` INTO the async block, AFTER the `cwdDropNoticeFor` drop-check, gated
on `notice === null`. Reuse the existing pure reducers (cwd-save-outcome.ts `cwdDropNoticeFor`,
session-restart-prompt.ts `restartPromptIdFor`) — the `promptId` is still computed from the PRE-save row
synchronously (before ptyUpdateProfile overwrites the launch fields), but the SET is deferred behind the
drop-check so the drop wins.

Purpose: an invalid cwd at Save shows the inline reminder, keeps the modal open, and never pops the restart
prompt first — closing the operator's #3 re-gate failure ("wrong interface logic - the restart window popup first").
Output: the handleSaveProfile precedence fix + a renderer regression pinning the save-time ordering.
</objective>
