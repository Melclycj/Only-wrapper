Root cause (code-confirmed, 12-VERIFICATION.md): the Save button (`SessionEditModal.tsx:339`) carries BOTH

drop `context-menu-item` and the blue ramp wins.

rhythm, calm-by-default validation, and a visual gate that cannot pass without seeing the primary action.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer DOM events → modal close | A mouse gesture (drag-select) crossing into the overlay must not be misread as an intentional cancel |
| renderer form state → display | Validation strings are fixed literals + main's already-sanitized notice; rendered as React text nodes (auto-escaped) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-04-01 | Tampering | `.modal-overlay` onClick | mitigate | Close only when mousedown AND click both target the overlay itself (e.target===e.currentTarget) — a drag-select overshoot can no longer trigger an unintended cancel/data-loss |
| T-12-04-02 | Information disclosure | `.edit-field-notice` error text | accept | The cwd-rejection string is main's already-sanitized notice (sanitizeNotice strips C0/C1); rendered as a React text node, no HTML interpolation — no new surface this plan |
| T-12-04-03 | Spoofing | data-testid driven Save click | accept | Test-only hook; the security boundary (ptyUpdateProfile validate-in-main) is unchanged; no bridge key touched (EXPECTED_API_KEYS stays 20) |

## Reliability & Cost (§6.5) — light for this plan
This is a CSS/markup + test-harness change. No retry storms, no concurrent invocation, no unbounded resource,
no failure cascade, no cost runaway, no capacity ceiling. The only runtime behavior changed is a renderer click
predicate (the overlay guard), which is O(1) per click. No PTY/xterm/fit path touched (Core Value safe by
construction — the form is a modal).
</threat_model>
