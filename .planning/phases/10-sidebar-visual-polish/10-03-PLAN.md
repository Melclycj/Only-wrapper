<objective>
Fold in the two definite Gap-4 fixes from the Phase-9 human gate (no design debate): D-14 — the
right-click context menu must open at the cursor without overlapping the sidebar header (clamp
to viewport); and D-15 — the destructive Remove/Delete menu item must read in the danger ramp,
consistent with the destructive Delete affordance. Runs parallel to Plan 02 (different files —
ContextMenu.tsx / SessionManager.tsx / the context-menu CSS in terminal.css; zero overlap with
Sidebar.tsx / sidebar.css).

Purpose: The menu is the ONLY control surface in the collapsed rail; a menu that lands over the
sidebar header is a real usability defect the operator flagged. The danger color makes the
destructive choice unmistakable. Both are scoped, no-debate fixes — the full app-wide
danger/interaction-state sweep stays Phase 13.

Output: `ContextMenu.tsx` (measure-then-clamp via the Plan-01 `clampToViewport`; a `danger`
item variant rendering `.context-menu-item-danger`), `SessionManager.tsx` (set `danger: true`
on the Remove + Delete items), and the `.context-menu-item-danger` CSS rule in terminal.css.

ROOT-CAUSE CONFIRMED (RESEARCH A4, verified at source): ContextMenu.tsx renders
`style={{ left: x, top: y }}` with raw `clientX/clientY` (L87), passed straight through from
Sidebar.tsx's `onContextMenu(s.logicalId, e.clientX, e.clientY)` (L242-245) → SessionManager
`menuState.x/y` (L337-342) → ContextMenu. There is NO clamp anywhere; a right-click near the
top/left lands the menu over the header. The fix is a measure-then-clamp step ONLY — the
existing focus-first-item / Esc / click-outside / roving-arrow logic (L42-79) is untouched.
</objective>
